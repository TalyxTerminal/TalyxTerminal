# Quant runtime materials

This folder pins the native research and strategy runtimes [Quant](../README.md) uses: locks, identity files, upstream sources, patches, patched wheels and licenses.

## Environments

| Environment | Lock | Python | Used for |
|---|---|---|---|
| Research | `research.lock` (input `research.pins.txt`, identity `identity.json`) | 3.12 | Notebook kernels, research runs, factors / models / portfolios / statistics / pricing. Qlib, Alphalens, skfolio, QuantLib, ORE, statsmodels, arch, linearmodels, MLflow, ipykernel and jupyter_client are all included; nothing to choose |
| Strategy | `strategy.lock` (identity `strategy.identity.json`) | 3.13 | Nautilus backtests; see [Nautilus runtime](#nautilus-runtime) |
| Deep learning | `deep-cpu.lock` / `deep-cuda.lock` / `deep-xpu.lock` (identity `deep.identity.json`, generated by `build_deep_locks.py`) | 3.12 | Neural network models. The research lock plus PyTorch 2.15 (CPU, CUDA 13.2 or Intel XPU, chosen by the devices on the machine). The locks have no index lines; packages not on PyPI are written as direct links with a single hash. Regenerate them whenever the research lock changes |

The research environment is one lock and one environment: 214 packages (including PySCIPOpt 6.3.0, which bundles SCIP and has Windows wheels), no conflicts under `uv pip check`, about 1.1 GB installed. The first preparation downloads and installs everything in about 6 minutes; with a warm uv cache, about 45 seconds. pandas is 2.3.3 (the version Qlib, skfolio and Alphalens all work with) and NumPy 2.5.4. Both `cvxpy` and `cvxpy-base` are in the lock and their versions must match (skfolio depends only on `cvxpy-base`; the solvers on the Qlib side need the full `cvxpy`). For pricing work, use QuantLib directly in notebooks.

`identity.json` records the pinned Qlib source commit `54355232463878d2eebb91fe0ee5fa7fa1f5976c` (v0.9.8), the hash of the upstream skfolio 1.8.1 wheel, and the versions and source commits of QuantLib 1.43 and ORE 1.8.16.0. Upstream wheels and source archives are in `upstream/`, the limited patches in `patches/`, and patched wheels in `wheels/`. Original copyright notices, METADATA and licenses are preserved; standalone license texts are in `licenses/`. Qlib is MIT, Alphalens-reloaded Apache-2.0, skfolio and statsmodels BSD-3-Clause, arch and linearmodels NCSA; ORE and QuantLib follow their own license files.

The Qlib patch only adds a report date-format parameter, and the Alphalens patch only adds an annualization parameter; both keep the original default behaviour. Qlib portfolio backtests for models pass the number of bars per year from the Market calendar explicitly to the native `risk_analysis` (instead of Qlib's A-share default of 238), without copying the computation. Intraday charts, 365-day markets and mixed-market parameters are still expressed by the actual research configuration.

Alphalens is 0.5.1. It fixes the trading calendar being lost after factor cleaning (intraday data is no longer padded to the calendar). Annualization at 252 days is still hard-coded in `factor_alpha_beta`, so the annualization patch is still needed; the same patch applies unchanged to 0.5.1. Since 0.5.0, the group return spread is computed on 100% gross exposure (half of the earlier convention), so results are not directly comparable with older versions.

## Locks and local wheels

Local wheels in `.in` / `.lock` / `research.pins.txt` files are written relative to the repository root as `file:./modules/quant/runtime/wheels/...`. Before installing, Quant replaces them with the current repository's actual path in `bundled_wheels` in `backend/native_environment.py` (absolute paths in older project locks are handled the same way), and `--hash` still verifies the wheel bytes. Running `uv pip install -r modules/quant/runtime/<name>.lock` from the repository root also works directly.

Normal operation consumes the provided wheels and locks and needs no compilation. To rebuild the patched Qlib / Alphalens wheels, use `scripts/build_research_runtime.py`. To rebuild the original Qlib wheel, use `build_qlib_upstream.py`; the Microsoft build tools are prepared by `tools/native-build/prepare.py` from pinned sources and hashes (see [tools/native-build/README.md](../../../tools/native-build/README.md)), and output goes to `output/quant-native-build/`.

## Nautilus runtime

The wheel is built from the official Nautilus sdist (2.0.0rc8) with dYdX removed and with fee fixes, generic instrument trading conditions, reference-price trigger conditions and build support added. It is a complete high-precision Windows cp313 runtime, version `2.0.0rc8+talyx.20`, used by the strategy lock `strategy.lock` (identity `strategy.identity.json`). The wheel goes in `wheels/` and the full source used for the build in `upstream/`; patches and build records are in `patches/`. The wheel and the source archive are build artifacts and are not tracked in the repository.

Changes from the official rc8:

| Change | Why |
|---|---|
| dYdX removed (workspace `exclude`, dependencies and Cargo.lock kept in sync, maturin excludes its Python adapter) | Not needed; saves build time and size |
| A private `_generate_type_stubs` on `_libnautilus`, which the build script uses to generate type files from the same DLL | The wheel ships `.pyi` files that match the binary |
| Fee fix: both risk checks and matching include fees in the funds a cash account needs to buy | The official cash account rejects negative balances, which interrupted backtests |
| Generic instrument trading conditions: quantities, date conditions, price bounds, sellable quantity and a per-order fee ledger | Stock trading rules applied inside the shared matching engine, keeping frozen quantities and fees already paid |
| Independent MARK / INDEX triggers | Reference prices only decide trigger conditions; candidate fill prices and liquidity still come from the execution book |

The stock-conditions patch adds an `Equity.info.execution_conditions` JSON input. Its rules contain only numeric conditions and confirmed sessions; they do not identify exchanges, boards or corporate actions. In the Cache, `trading-conditions/rules/<instrument>` can update the rules and `trading-conditions/state/<instrument>` exports the session, held and frozen quantities, and the per-order commission and tax ledger.

For every candidate fill, matching first filters by price bounds and sellable quantity, then consumes native liquidity. Protective orders stay alive while restricted; market orders exit with their native final state. The stock fee model replaces the zero model registered at setup with the instrument's conditions, and risk checks and final fill funds checks use the same accumulated fees. Research bars and execution bars can be separated by an explicit mapping or by frozen raw OHLCV, and the strategy cache keeps research prices.

Fee fix behaviour:

- **Risk checks:** for buy orders on a cash account (no borrowing), the funds required are the notional plus the estimated fee. The estimated rate is read from `taker_fee` in the instrument's `info` (a decimal string such as `"0.001"`, written by whoever defines the instrument from the venue's rate; Quant backtests write the venue taker rate into the instrument terms in `object_data.venue_for`, and `strategy_research.instruments` puts it in `info` when creating instruments). If it is missing, the fee is taken as zero; if it is invalid (not a number, negative, or ≥ 1), the order is rejected. Order amendments are estimated the same way.
- **Matching** (the `OrderMatchingEngine` used by the backtest's simulated exchange): for spot and stock fills on a cash account (no borrowing), if a fill plus its fee would make any currency balance negative, the fill is reduced to the largest affordable quantity (rounded to the instrument's minimum order unit; below the minimum order size counts as unaffordable), and the rest of the order is cancelled. If nothing is affordable, an unacknowledged order is rejected and an acknowledged one is cancelled. The order receives no further fills. The account never records a wrong balance.
- Only spot (`CurrencyPair`, non-inverse) and stocks are affected. Margin accounts, accounts that allow borrowing and other instrument types keep the official behaviour.

### Building a new version

The entry point is [build/nautilus.py](build/nautilus.py), run with CPython 3.13 from the repository's `.venv`. It downloads pinned tools and compiles natively; it is only needed when there is a new patch:

```powershell
& .\.venv\Scripts\python.exe -B modules/quant/runtime/build/nautilus.py prepare --base official:2.0.0rc8 --version <version> --patch <patch file>
& .\.venv\Scripts\python.exe -B modules/quant/runtime/build/nautilus.py build
& .\.venv\Scripts\python.exe -B modules/quant/runtime/build/nautilus.py publish --lock strategy
```

- The starting point `--base` is `official:<version>` (the official sdist) or an already published TalyxTerminal version. The official sdist lacks the three patched Cargo crates (`patches/`) and `python/pyproject.toml`; the script fetches them from that version's tagged commit and checks them against the digests in `build/sources.json`, which also holds the sdist and commit SHAs. Patches are in `git diff` format, relative to the tree after `prepare`.
- The source is kept in `output/native-build/nautilus/source` and the Cargo target in `output/native-build/nautilus/target`; downloaded tools and the Cargo cache are in `cache/` next to them. Running `prepare` again rewrites only files whose bytes changed, and Cargo rebuilds only affected crates. After changing a patch, repeat `prepare` + `build` without changing folders or bumping the version.
- `build` runs in parallel by CPU core count by default (adjust with `--jobs`). The feature list is the `FEATURES` constant. `coinapi`, a data adapter new in rc8, is not compiled in. The `defi`, `hypersync`, `postgres` and `redis` features are compiled in but not used by Quant; removing them must be validated together with a patch.
- `publish` is the only way to produce a release wheel. It requires the build tree to equal the base plus the recorded patches exactly, and the version must not have been published before. It then copies the wheel, source archive, patch and build record, and registers them in `build/sources.json`. `--lock` also points the matching `.in` / `.lock` and identity file at the new wheel (with status `validation_pending` until it has been validated); without it, the wheel is only published, and `adopt --version <version> --lock <lock>` switches later.
- The version line is set by `--version`; patches must not change it.
- The tool lock is `build/tools.json` (Rust 1.99.1, required by rc8; CMake, NASM, maturin). MSVC and the Windows SDK come from `tools/native-build/prepare.py`.
